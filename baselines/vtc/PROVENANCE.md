## What the artifact actually is

The repository is **not** a standalone VTC implementation — it is a fork of
**S-LoRA** (`S-LoRA/S-LoRA`, "Serving Thousands of Concurrent LoRA
Adapters," arXiv:2311.03285), a full GPU serving engine with custom CUDA
kernels (Triton `bgmv` batched matrix-multiply kernels for heterogeneous
LoRA-adapter batching), into which VTC and several baseline schedulers are
added as alternative request-queue/scheduler implementations. Different
**clients/tenants are modeled as different LoRA adapters** (`adapter_dir`
is the tenant identity throughout the code); the paper's own experiments
disable actual LoRA computation via a `--no-lora` server flag for a
"vanilla" (non-LoRA) fairness evaluation, since VTC's fairness algorithm
makes no assumption about LoRA at all — LoRA-adapter identity is reused
purely as a convenient multi-tenant identifier already present in the
S-LoRA codebase.

**Requirements** (from `README.md` top-level Requirements section and
`fair_bench/README.md`'s artifact-evaluation instructions):
- CUDA 11.8-compatible GPU, Ampere family (A100) recommended; Turing (T4,
  no bfloat16) explicitly unsupported.
- `1.13 <= PyTorch <= 2.0.1` (top-level README) / PyTorch 2.1.2 recommended
  specifically for the artifact-evaluation instructions in
  `fair_bench/README.md`.
- `triton==2.1.0` (pinned exactly, not a floor).
- Custom CUDA extension `slora._kernels` (`bgmv` ops), built via
  `torch.utils.cpp_extension.CUDAExtension` at `pip install -e .` time.
- Hardware used in the paper's own artifact-evaluation instructions: one
  AWS A10G (24GB) and one A100 (80GB) instance.

**Supported models:** Llama-7B (settings S1/S2), Llama-13B (S4), Llama-30B
(S5), Llama-70B (S6) — S-LoRA's own model-setting table, with 1–4
simultaneously served LoRA adapter ranks per setting. VTC's fairness
scheduler is model-agnostic; the model choice only affects the underlying
S-LoRA engine's throughput, not the scheduling algorithm.

**Workloads and datasets:** Synthetic traces generated by
`fair_bench/exp_suite.py` (named suites: `overload`, `proportional`,
`on_off_less`, `on_off_overload`, `poisson_short_long`,
`poisson_short_long_2`, `increase`, `dist_shift`, plus ablation suites), and
one real trace (`fair_bench/real_trace.pkl`) sampled from
`chat.lmsys.org` (LMSYS Chatbot Arena) — the official README discloses that
**prompt text in the real trace is masked** ("Hello Hello Hello ...", real
arrival timestamps and token lengths preserved) for privacy, and that the
*original* submission-era real trace was lost, so the shipped one is
resampled from a different time range ("the plots... looks different...
[t]he trends and conclusion are maintained same" — official README's own
wording).

**Official commands:** `python launch_server.py [--scheduler vtc|slora|...]
[--no-lora] [--num-adapter N]` then `python run_exp.py --suite <name>
--output <path>.jsonl`, then `python plot/plot_*.py` — full instructions in
`fair_bench/README.md` (reproduced in full in
`baselines/vtc/official_reference/artifact_evaluation_readme_excerpt.md`).

**Official metrics:** per-client cumulative service received over time
(the paper's primary fairness visualization — "accumulated service
difference" between clients), per-client response-time distributions,
overall throughput, and (Section 6.4 ablation only) service difference vs.
memory-pool size / max request length.

**Pretrained assets:** none required or shipped. VTC is a pure algorithmic
scheduler (no learned component) — this is a structural difference from
`baselines/pars/` and `baselines/vllm_ltr/`, both of which wrap a trained
predictor. The repository ships only code, synthetic-trace generators, and
one masked real trace; it does not ship or require any model checkpoint of
its own (the *base LLM* weights, e.g. Llama-2-7B, are downloaded separately
and are orthogonal to VTC itself).

## Hardware blocker for direct/wrapped full-system execution

This development machine's GPU is an **NVIDIA GeForce RTX 5060 Ti**
(Blackwell architecture, compute capability sm_120), driver 580.173.02,
with PyTorch 2.12.0+cu130 (CUDA 13.0) installed system-wide. The official
artifact requires CUDA 11.8, PyTorch ≤2.1.2, and `triton==2.1.0`.

This is a **harder blocker than a version mismatch to work around**: CUDA
11.8's `nvcc` toolchain predates Blackwell hardware entirely and cannot
target `sm_120` at all (no `-arch=sm_120` support exists in that compiler
generation), and `triton==2.1.0` likewise predates Blackwell PTX/SASS
codegen support. The custom `slora._kernels` CUDA extension (the `bgmv`
kernels S-LoRA needs for LoRA-adapter batching) cannot be compiled for this
GPU under the artifact's required toolchain, full stop — no environment
variable fix, container with an old CUDA *runtime*, or dependency-pinning
trick changes this, because the constraint is "this compiler generation
never learned this GPU architecture exists," not "these library versions
disagree." This is categorically different from, and more fundamental
than, the version-skew issues resolved for the real-vLLM baseline pilot
(see this project's `vllm_real_external_baseline_pilot` memory), which were
ordinary software-version conflicts on hardware the software already
supported.

**Consequence:** direct official-system execution (running
`launch_server.py`/`run_exp.py` end-to-end, i.e. classification 1) is not
currently achievable on available hardware. A full "wrap the official
binary" integration (classification 2, in the literal sense of driving
their actual GPU inference server as a subprocess) is equally blocked by
the same compile failure, since that server *is* the thing that needs the
CUDA extension.

## Why this blocker does not block a faithful integration

VTC's fairness-scheduling **algorithm** is implemented entirely in
`slora/server/router/vtc_req_queue.py` (`VTCReqQueue`, subclassing
`slora/server/router/req_queue.py`'s `ReqQueue`) — pure Python + NumPy,
with **zero** dependency on the compiled CUDA extension, Triton, or a GPU.
Its own imports (`slora/server/io_struct.py`'s `Req`/`Batch`,
`slora/server/sampling_params.py`'s `SamplingParams`,
`slora/utils/infer_utils.py`) are likewise pure Python; the one `torch`
import in `infer_utils.py` is used only inside an unused-here debug-timing
decorator (`mark_cost_time`, never invoked by `vtc_req_queue.py`, which has
its own `@calculate_time` decorator call commented out) and inside
functions never reached by the scheduling code path. This was verified
directly: the official, **unmodified** `VTCReqQueue` class was dynamically
imported from the pinned clone (via `importlib.util.spec_from_file_location`,
with a minimal synthetic package hierarchy so its relative imports
resolve — no source file copied, edited, or reformatted) and exercised in
this project's plain CPython 3.12 environment, with no GPU, no CUDA
extension, and no Triton installed. It ran correctly:

```
q = VTCReqQueue(max_total_tokens=10**9, batch_max_tokens=10**9,
                running_max_req_size=1000, adapter_dirs=["A","B"],
                fair_weights=[1,1], cost_func="linear")
q.append(Req("A", 1, [0]*10, SamplingParams(max_new_tokens=5)))
q.append(Req("B", 2, [0]*10, SamplingParams(max_new_tokens=5)))
b = q.generate_new_batch(None, {"A": 0, "B": 0})
# -> both requests admitted, q.served == {"A": 10.0, "B": 10.0}
```

This confirms the fairness **policy** (the paper's actual intellectual
contribution and this integration's actual target) is fully decoupled from
the GPU serving-engine layer that is currently unbuildable on this
hardware. See "Integration classification" below.

## Algorithm audit

Read directly from `slora/server/router/vtc_req_queue.py` and its parent
`slora/server/router/req_queue.py` at the pinned commit.

**Service-accounting state** (`VTCReqQueue.__init__`):
- `self.served: Dict[adapter_dir, float]` — cumulative virtual "cost"
  counter per tenant (the core VTC state; lower = less served so far,
  relative to its fair share).
- `self.user_req_list: Dict[adapter_dir, deque[Req]]` — one FIFO queue per
  tenant.
- `self.fairw: Dict[adapter_dir, float]` — static per-tenant fairness
  weight, set once at construction from the `fair_weights` list aligned to
  `adapter_dirs` (default 1.0 for any adapter beyond the supplied list).
- `self.input_price` / `self.output_price` — global per-token price
  multipliers (defaults 1 and 2: a decode token costs twice a prefill
  token by default, reflecting real batched-serving compute asymmetry).
- `self.cost_func` — `"linear"` (raw token counts × price) or `"profile"`
  (a hardware-calibrated regression `cost_func_profile(x, y) = 0.21001891x
  + 0.10075395y + 0.0039868xy + 0.00324733y² + 1.14601454`, `x`=input
  tokens, `y`=output tokens so far, inherited from `ReqQueue` — fit to
  their specific A10G + Llama-2-7B setup and not portable).

**Scheduling rule** (`generate_new_batch`): repeatedly select
`adapter_dir = min(active_served, key=active_served.get)` among tenants
with a non-empty waiting queue; pop that tenant's head-of-line request; if
it is aborted, drop it for free (no cost charged) and continue; otherwise,
if it passes the memory-feasibility gate (`_can_add_new_req`, inherited
from `ReqQueue`) and the running batch's token budget, admit it and charge
its full `input_len` cost immediately to `self.served[adapter_dir]` (and to
a local `active_served` copy, so the next iteration's `min()` reflects the
update within the same batch-formation pass); otherwise stop (the batch is
full for this step). This is a **greedy, work-conserving, min-served-first**
loop — closer in spirit to Weighted Fair Queuing / Start-time Fair Queuing
than to a priority-heap scheduler, and it decides admission order, not just
a priority label.

**Fairness objective:** bound the maximum service-received difference
between any two continuously-backlogged clients to a small constant factor
(the paper's Theorem states a 2×-tight bound), while remaining
work-conserving (never idles capacity while feasible backlogged work
exists). This is a max-min-fairness-flavored guarantee, not a
throughput-maximizing or SLO-attainment objective — VTC can and does trade
raw throughput for equalized service.

**Normalization/weighting:** every cost increment is divided by
`self.fairw[adapter_dir]`, so a tenant with weight `w > 1` accrues its
counter `w` times slower per unit of actual work served, causing the
min-served selection to favor it — this is how per-tenant priority weights
enter VTC (evaluated as "WVTC" in the artifact's own `fair_bench/WVTC/`
results directory).

**Tie-breaking:** **not** an explicit rule anywhere in the paper or code —
it is an artifact of `min(active_served, key=active_served.get)`: Python's
`min()` returns the *first* key achieving the minimum value in dict
iteration order, and dict iteration order is insertion order. `self.served`
keys are inserted in the order each tenant's queue first became non-empty
(inside `append()`). A faithful reimplementation of the *interface* must
reproduce this exact insertion-order tie-break, not e.g. tenant-ID sort
order — but because this integration dynamically imports and calls the
*actual* unmodified `VTCReqQueue` object (not a reimplementation), this
tie-break is inherited automatically and requires no separate replication.

**Interaction with continuous batching:** two separate hooks, both called
every scheduler step by the S-LoRA router loop: `generate_new_batch`
(admission — called once per step to fill the batch up to capacity) and
`update_counter` (decode-cost accrual — called once per decode iteration,
for every request currently in the running batch, adding a flat
`1 * output_price / fairw[adapter_dir]` per call under `cost_func="linear"`,
or the profiled marginal delta under `"profile"`). Both directly mutate the
same `self.served` dict; there is no separate "ranking" step distinct from
admission — the admission loop *is* the ranking.

**Prompt/decode token accounting:** prompt (input) tokens are charged in
one lump sum **at admission time** (`req.input_len * input_price`); output
tokens are charged **incrementally, one unit per decode iteration**, by
design (decode recurs every step while prefill is a one-time cost).

**Prefix caching:** **not modeled anywhere in this code path.** No
radix-cache or prefix-sharing accounting exists in this artifact — every
request's `input_len` is charged in full regardless of any token-prefix
overlap with other requests, and the underlying S-LoRA engine this is
built on does not implement automatic prefix caching (unlike vLLM's
`APC`/SGLang's RadixAttention, which postdate/are contemporaries of this
codebase). This is a scope limitation of the **official artifact itself**,
carried through unmodified into this integration — not something this
integration added or removed.

**What VTC changes vs. base `ReqQueue` (FCFS):** admission order (which
waiting request is picked next), by extension the composition of each
batch (ranking *is* admission here), and nothing about decode-execution
mechanics themselves (KV memory paging, kernel dispatch) — those are
inherited unmodified from the base engine. VTC does not touch anything
downstream of "which request enters the batch this step."

**Runtime state unavailable in this project's simulator, confirmed by
direct inspection of `src/llmserveopt/core/types.py`:**
1. **No tenant/client identity concept anywhere.** `Request` /
   `ObservableRequest` have zero fields for multi-tenancy (`grep -rn
   "tenant" src/llmserveopt/core/*.py` → no matches). The closest existing
   field is `class_id: str` (documented as an SLO-tightness label: "tight",
   "medium", "loose"), which is unused by any accepted canonical workload
   for tenant purposes.
2. **No native per-decode-iteration hook exposed to policies.**
   `BasePolicy.select_action()` is invoked only at admission-decision
   steps, not once per decode tick the way the official S-LoRA router
   calls `update_counter`. Decode-cost accrual must instead be
   reconstructed between admission calls from
   `ObservableGPUState.tokens_decoded_per_request` deltas.
3. **Different KV-memory feasibility model.** The simulator's own
   `BasePolicy._feasible_on_gpu` is a simple additive check
   (`current_kv_tokens + prompt_tokens <= max_kv_tokens`); the official
   `_can_add_new_req` is a worst-case, sorted-cumulative check across all
   requests' *remaining* decode lengths, and it is entangled with
   S-LoRA-specific LoRA-adapter memory-pool bookkeeping
   (`lora_ranks`, `adapter_size`) that has no meaning once LoRA is
   disabled (as this project's use does, matching the paper's own
   `--no-lora` "vanilla" mode).

**Assumptions required by the fairness theorem** (all directly visible in
the code): (a) work-conserving scheduling — the admission loop never idles
while feasible backlogged work exists; (b) the "counter lift" rule in
`append()` — when a tenant's queue transitions from empty to non-empty
(i.e. it was inactive and just returned), its `served` counter is raised
to at least the minimum `served` value among *other* currently-active
(non-empty-queue) tenants, preventing an inactive tenant's counter from
falling arbitrarily far behind and then monopolizing the scheduler on
return; (c) a single, monotonic, shared cost function applied identically
to every tenant.

**Core files implementing the policy:**
`slora/server/router/vtc_req_queue.py` (`VTCReqQueue` — the entire
algorithm) and `slora/server/router/req_queue.py` (`ReqQueue` — base
class providing `_can_add_new_req`/`_init_cache_list`/`cost_func_profile`,
which `VTCReqQueue.generate_new_batch` overrides but still relies on the
inherited `_can_add_new_req`/`_init_cache_list`).

## Integration classification

**Official policy reused with simulator adapter.**

Preference order from the task instructions is (1) run official code
unchanged, (2) wrap official code, (3) reproduce only if unavoidable. (1)
and a literal-subprocess form of (2) are both blocked by the hardware issue
above — the full GPU serving engine cannot be built on this machine. But
(2) in the sense that matters for a *scheduling-policy* comparison — the
official, unmodified `VTCReqQueue`/`ReqQueue`/`Req`/`Batch`/`SamplingParams`
classes, dynamically imported from the pinned clone and called exactly as
authored (their `append`, `generate_new_batch`, `update_counter` methods
run verbatim, zero source edits) — **is** achievable and is what this
integration delivers. No line of the official scheduling algorithm is
reimplemented, approximated, or paraphrased; only the translation shim
around it (simulator `ObservableRequest` ↔ official `Req`/`Batch`) is new
code, exactly the same shape as `baselines/pars/adapter/ranking_adapter.py`
and `baselines/vllm_ltr/adapter/simulator_policy.py`'s existing pattern for
this project's other two external baselines.

This is explicitly **not** called "official VTC" running end-to-end, and
is not a mechanism-level proxy either — see
`docs/audits/vtc_official_artifact_audit_20260805.md` for the full,
disclosed list of deviations (LoRA-memory-gate bypass via all-zero
`lora_ranks`, single-monolithic-GPU-only scope, `cost_func="linear"` only,
decode-cost reconstructed from per-step deltas rather than a native
per-tick hook).
