# Runtime Validation Benchmark Pack

`experiments/runtime_validation_benchmark_pack/`, generated by
`scripts/build_runtime_validation_benchmark_pack.py`.

## Purpose

A compact, canonical, Git-friendly package of real-A100-hardware ground
truth, assembled entirely from already-completed and already-committed
Wulver experiment artifacts (`experiments/gpu_external_validity/`) — no
new GPU jobs, no reruns, no network access. It exists so that simulator
work (in particular building and validating the recommended
`vllm_chunked_prefill_faithful` baseline, see
`docs/vllm_chunked_prefill_faithful_design_audit.md`) can be evaluated
against fixed, checksummed real-hardware targets on a development machine
without needing Wulver/GPU access at all.

## Provenance: source jobs

All eight jobs referenced here were completed and analyzed in prior
sessions; this pack reorganizes their already-committed outputs, it does
not reprocess raw/uncommitted data.

- Models: `Qwen/Qwen2.5-7B-Instruct` (jobs 1111541/1111545/1111572),

## Scenario schema (`scenarios/<id>.json`)

```
{
  "canonical_scenario_id": str,        # short, stable id used across all 4 fixture types
  "category": str,                     # == canonical_scenario_id
  "positive_target": bool,
  "negative_control": bool,
  "sarathi_harness_name": str,         # name in scripts/run_sarathi_gpu_smoke_and_validation.py
  "vllm_harness_name": str,            # name in scripts/run_gpu_external_validity_audit.py
  "source_functions": [str, str],      # the two generator functions, verified byte-identical
  "prompt_seed": 20260719,
  "request_count": int,
  "max_client_concurrency": int,
  "arrival_order_by_request_id": [int, ...],
  "requests": [
    {
      "request_id": int,
      "arrival_time_s": float,
      "prompt_bucket": "short"|"medium"|"long",
      "target_output_tokens": int,
      "intended_prompt_tokens_approx": int,   # word-count heuristic, not exact tokenizer count
      "prompt_char_length": int,
      "prompt_sha256": str                    # verifies regenerated prompt text matches exactly
    }, ...
  ]
}
```

Full prompt text is **not** included (compact-fixture requirement).
Regenerate it deterministically via
`llmserveopt.real_llm.calibration_common.build_length_targeted_prompt`
using the same `prompt_bucket`/`target_output_tokens`/`seed=20260719`; the
`prompt_sha256` is the portable check that a regeneration is byte-identical
to what was actually run.

## Target-metric schema (`hardware_targets/<id>.json`)

Per scenario, per system (`sarathi`, `vllm`), per metric (`ttft_s`,
`tpot_s`, `e2e_s`): `n`, `mean`, `median`, `stdev`, `p50`, `p95` across the
N=5 repeated trials (jobs 1111988/1111989/1111990). Plus, for E2E
specifically: `winner_identity_e2e`, `winner_frequency_e2e`, paired
bootstrap 95% CI for the mean (vLLM − Sarathi) difference, and the
`robustness_classification` (`ROBUST`/`SUGGESTIVE`/`NOT_REPRODUCED`) from
`docs/wulver_sarathi_vllm_repeated_validation.md`'s stated (non-inferential)
classification rule.

## Simulator schema (`simulator_baseline_results/<id>.json`)

`vllm_faithful` and `sarathi_faithful` mean TTFT/E2E and completion
fraction (from job 1111706's already-computed `run_simulator_scenario()`
output — not rerun for this pack), the simulator's own E2E winner, the
robust hardware E2E winner, whether they match, and a `known_mismatch_reason`
where one is already documented.

## Positive targets and negative controls

- **`POSITIVE_TARGETS`**: `active_decode_plus_arriving_prefill`,
  `kv_pressure` — real hardware shows a **ROBUST** (5/5 trials, bootstrap
  95% CI excludes zero) Sarathi E2E advantage. A correct
  `vllm_chunked_prefill_faithful` (or any future simulator improvement)
  should predict Sarathi wins here. **The current
  `vllm_faithful`/`sarathi_faithful` pair gets both of these wrong**
  (predicts vLLM in both) — confirmed by this pack's own
  `simulator_baseline_results/` data, not just asserted.
- **`NEGATIVE_CONTROLS`**: `long_prompt_moderate_output`,
  `prefill_heavy_burst`, `mixed_prompt_lengths` — real hardware shows an
  equally robust vLLM E2E advantage (5/5 each). A correct simulator should
  predict vLLM wins here too, and — importantly for a negative control —
  should **not** show a false Sarathi advantage even after being extended
  to handle chunked prefill better. The current simulator pair gets all
  three of these right already.

## Long-context fixture (`long_context/xlong_context_burst16.json`)

16 requests, ~12,000-token prompts, 512-token target output, all arriving
at `t=0` (from job 1111572's `stress_xlong_context_burst16` scenario).
Real vLLM 0.24.0 (chunked prefill enabled) completes all 16
(`completion_fraction=1.0`). `vllm_faithful` (pinned to v0.1.0, no chunked
prefill, all-or-nothing admission against a fixed 2,560-token budget)
completes **zero** (`completion_fraction=0.0`, all 16 sit in `waiting`
forever). This is the direct acceptance-test target for
`vllm_chunked_prefill_faithful`'s admission behavior: it must complete this
fixture via genuine chunked admission, not vLLM v0.1.0's all-or-nothing
check.

## KV progression fixture (`kv_progression/kv_progression.json`)

Jobs 1111541 → 1111545 → 1111572, same model/GPU, deliberately varied
server config: peak KV utilization 2.22% → 13.96% → 83.67% (headroom 45.1x
→ 7.16x → 1.195x), **zero preemption events in all three**. Framed
explicitly as a **structural**, not timing, regression target: a
simulator/baseline checked against this fixture should reproduce the
*qualitative* fact that vLLM's admission control prefers queueing new
arrivals over evicting running work even at very low headroom (structural
fact), not any specific absolute latency number (not a timing target).

## Safe claims

- Every number in this pack traces to a specific, named, already-completed
  Slurm job ID, and every file's sha256/size is recorded in `manifest.json`
  for integrity checking.
- The pack is deterministically regenerable from already-committed source
  artifacts (`python scripts/build_runtime_validation_benchmark_pack.py`) —
  no GPU, no network, no new experiments.
- The positive-target/negative-control labeling is grounded in the
  repeated-trial (N=5) statistical results, not the earlier single-run
  observations — both positive targets were independently reconfirmed
  ROBUST across 5 trials each (`docs/wulver_sarathi_vllm_repeated_validation.md`).
- The current `vllm_faithful`/`sarathi_faithful` simulator pair
  demonstrably fails on both positive targets and passes on all three
  negative controls, using this pack's own data — a concrete, checkable
  acceptance bar for any future baseline improvement.

## Limitations

- All hardware-target statistics are N=5 trials per scenario/system —
  small-sample statistics, not large-scale benchmarking; bootstrap CIs are
  correspondingly wide relative to a larger-N study, even though they
  happen to exclude zero cleanly in every scenario tested here.
- Both models/configurations were chosen for this specific validation
  effort (Qwen2.5-7B-Instruct for the KV-pressure jobs, Mistral-7B-Instruct-v0.1
  for the Sarathi comparison, because the vendored Sarathi fork does not
  support Qwen2's architecture) — this pack does not claim these findings
  generalize to other models, GPUs, or vLLM/Sarathi versions.
- `intended_prompt_tokens_approx` in scenario fixtures is a word-count
  heuristic (`llmserveopt.real_llm.calibration_common.approx_token_count`),
  not an exact tokenizer count; real per-request tokenizer counts (where
  recorded) are in the original job artifacts under
  `experiments/gpu_external_validity/`, not reproduced here.
- The `kv_pressure` positive target's simulator mismatch has not been
  root-caused at the scheduler-algorithm level the way the
  `active_decode_plus_arriving_prefill` mismatch has (see
  `simulator_baseline_results/kv_pressure.json`'s `known_mismatch_reason`)
  — flagged, not resolved.
- This pack does not include Sarathi's structural model-architecture
  limitation (Qwen2 unsupported by the pinned fork) as a fixture — that is
  a build/compatibility fact, not a runtime-metrics comparison, and is
  documented in `docs/wulver_vllm_kv_pressure_results.md` instead.

## Regeneration and verification

```
python scripts/build_runtime_validation_benchmark_pack.py
```

To verify an existing pack's integrity against its manifest:

```python
import hashlib, json
from pathlib import Path
root = Path("experiments/runtime_validation_benchmark_pack")
manifest = json.loads((root / "manifest.json").read_text())
for f in manifest["files"]:
    actual = hashlib.sha256((root / f["path"]).read_bytes()).hexdigest()
    assert actual == f["sha256"], f["path"]
```
