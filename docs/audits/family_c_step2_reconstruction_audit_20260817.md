## 3. Three Separate Objects

**A. Scenario reconstruction (request-level inputs).** This is where the
divergence lives, confirmed by the forensic audit's own metric-differential
analysis and re-verified here by direct read of
`kv_v2_reproducibility_forensic_20260817.md` §C: `bulk_n`/`urgent_n`
(population **counts**) match exactly on all 144 historical-vs-current
rows, and `completion_fraction` matches exactly on all 144 — but
`n_steps` and `peak_kv_utilization` differ on essentially every row. Since
request *counts* and arrival-class composition are unaffected while
KV-occupancy-trajectory metrics (which are driven by per-request
`prompt_tokens`/`predicted_output_tokens`, i.e. sampled BurstGPT token
lengths) differ substantially, **the divergence is isolated to the
sampled-token-length stage of scenario construction, not to arrival
mechanics, class assignment, or request counts.**

**B. Policy execution (given identical scenarios).** Not separately
testable for the historical scenarios (since they cannot be reconstructed,
§2), but testable for *reconstructibility of the harness itself*: two
independent fresh full reruns of the KV v2 generator+simulator pipeline in
the current environment produced byte-identical output
(SHA-256 `e6303d854b2e4f158cd388a85a86833e1902a2b717f3e4c8a9edf894f3285bf2`
both times — forensic audit §E, re-confirmed by this task's own read of
that section). Given identical scenarios, policy execution and metric
aggregation are fully deterministic and reproducible.

**C. Metric aggregation.** Same conclusion as B — the pipeline from
completed-request list to `RunMetrics` is deterministic and unchanged
(zero code diff, forensic audit §D).

**Earliest divergence: scenario construction's BurstGPT token-length
sampling step**, specifically `_load_burstgpt_arrays()`'s resolved file
content (`templates_prefill_decode.py:113-126`, shared by Family C) — not
policy code, not simulator code, not metric code, not RNG call order (§6).

## 6. RNG / Sampling Determinism

`case_kv_pressure_reserve_contention_v2` (`templates_kv_pressure_v2.py:120`)
constructs `rng = np.random.default_rng(seed)` — a **local, per-call
Generator instance**, not global `np.random` module state. This is the
determinism-safe pattern: scenario generation for one `(bulk_pressure,
urgent_arrival_phase, urgent_tightness, seed)` cell cannot be perturbed by
the order in which other cells were generated, by grid iteration order, or
by which process/worker executed it. This is confirmed by (and gives a
concrete mechanism for) the forensic audit's own §F finding that `--workers
1` and `--workers 4` reruns show identical mismatch counts — scenario
construction happens per-call with no shared mutable RNG state to race on.

`_load_burstgpt_arrays()` (`templates_prefill_decode.py:113`) is called
fresh inside every scenario-construction call (72 times per full pilot run,
not cached/shared) — this rules out a "first-call vs. later-call" ordering
effect on pool construction too. **RNG/call-order hypotheses (§6's original
concern list) are ruled out as an explanation, definitively, not just
narrowed.**

## 7. Historical Data-Staging State

`resolve_burstgpt_path()` (`templates_prefill_decode.py:129`) is a thin
delegate to `_get_staged_burstgpt_path()` — a path-resolution function, not
a data transform. `_load_burstgpt_arrays()` itself does
`pd.read_csv(path_str, nrows=30000)` → `detect_burstgpt_schema()` column
detection → `pd.to_numeric(..., errors="coerce").dropna()`. **No
filtering, concatenation, truncation, or intermediate-cache step exists in
this code path beyond what's already characterized in the forensic audit's
§G** (which already tested both real candidate files directly and found
neither reproduces history, narrowing the live hypothesis to "a third,
no-longer-present file/staging state" or "an unrecorded pandas/numpy
version difference in `pd.to_numeric`/`dropna` behavior" — forensic audit
§H items 1 and 3). This task's code-path re-read confirms there is no
missed transform step to find; the remaining hypotheses in §H are about
**data or environment state that no longer exists to inspect**, not about
undiscovered code logic.

Current environment's exact library versions, for provenance (not recorded
historically, so this cannot itself close the gap, but is now on record for
any future comparison): `numpy==2.4.4`, `pandas==3.0.2`.

## 8. Does MF-PSD v1 Contain Enough Information for Exact Replay?

No, by design. `mf_psd_scenarios_v1.csv`'s Family-C columns
(`feat_C__bulk_pressure`, `feat_C__urgent_arrival_phase`,
`feat_C__urgent_tightness`) are the three *swept grid factors* — sufficient
to identify which cell of the config grid a scenario belongs to, but not
the per-request sampled `prompt_tokens`/`predicted_output_tokens` values
(MF-PSD v1 §D documents this: `source_scenario_features_json` for Family C
is "derived from `per_policy_results.csv` itself", i.e. aggregate
per-scenario fields like `bulk_n`/`urgent_n`, not a request-level dump).
This matches MF-PSD v1's own explicit, documented limitation (§P item 4:
scenario-level features are whole-trajectory aggregates) and was never
intended to support byte-exact replay. **No silent reconstruction from
aggregate features was attempted or is being proposed** — confirming the
same conclusion as §2/§5 through a different artifact.
