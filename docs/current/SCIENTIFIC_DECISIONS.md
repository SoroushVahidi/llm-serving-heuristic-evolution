# Scientific Decisions — Summary

A summary of high-impact decisions only. This does **not** replace the full
decision log (`docs/contextual_composition_decisions.md`, entries `CCD-001`
through `CCD-024` as of this writing) — it is a fast-read index into it. No
new scientific decisions are introduced by this document; every row below
is already recorded, with evidence, at its source.

| Decision | Rationale | Evidence | Consequence | Source |
|---|---|---|---|---|
| CC5 finalized as regime-specific, not full | Point-estimate superiority over `best_global_composition` was not statistically distinguishable from zero (p=0.5654); a paired-significance requirement was built into the verdict logic itself, not applied after the fact | Frozen operating-envelope gate, 76 held-out windows, paired 95% CIs vs. best-fixed (p<0.0001) and hard selector (p=0.021) | Classification is `COMPLETE_REGIME_SPECIFIC`; full-context superiority must not be claimed | `CCD-019`, `docs/audits/contextual_composition_cc5_final_operating_envelope_20260803.md` |
| CC6 blocked pending external-baseline checkpoint | Starting dynamic-adaptation work before the current external-baseline evidence base is checked would risk building on an incomplete comparison set | CC5's own restricted-scope framing; the roadmap's standing "do not begin CC6 implementation until a future query explicitly authorizes it" instruction | CC6 remains queued, restricted to 7 trusted regimes, not started | `docs/contextual_composition_roadmap.md`, `docs/current/NEXT_ACTIONS.md` |
| VTC is a foundational candidate, not registered | Wins/ties the fairness (Jain's-index) comparison in 17/18 family×seed combinations using the real, unmodified official `VTCReqQueue`, but only via an adapter wrapper — registration as deployable requires a native reimplementation first | 108-run headroom-gated sweep, 45/45 fidelity/micro-trace/headroom tests, independently re-verified with zero mismatches | Scientific classification `FOUNDATIONAL_CANDIDATE`; deployment status remains `EVALUATION_ONLY` until native reimplementation | `docs/audits/vtc_fairness_comparative_evaluation_20260805.md` |
| PARS-Serve-2026 and vLLM-LTR are evaluation-only | Both have complete, independently verified evaluations, but neither wins any discriminative regime against this project's own strongest internal policies | 8-family canonical-suite sweep (PARS); WildChat-control sweep (vLLM-LTR) | Both remain `EVALUATION_ONLY` — useful comparison points, not selector candidates | `docs/audits/pars_first_comparative_evaluation_20260804.md`, `docs/BASELINE_STATUS.md` |
| Sarathi is mechanism-level validated, with a known simulator limit | The real-hardware decode-protection mechanism cannot be reproduced inside this simulator under FCFS-strict admission — verified as a structural limitation, not chased further as a bug | Real Wulver A100 repeated-trial comparison (N=5) vs. simulator behavior; documented root-cause analysis | Stress-test gates revised to a coarser, still-genuinely-discriminating check rather than pretending the mechanism reproduces | `docs/wulver_sarathi_vllm_repeated_validation.md`, `docs/research/algorithm_stress_tests/SARATHI_MECHANISM_CALIBRATION_20260805.md` |
| Apt-Serve integration strategy (C vs. D) unresolved | Deciding this from source-code reading alone would undermine the entire point of running the probe — an explicit, standing project instruction | Audit + fully prepared, unexecuted probe infrastructure; Wulver access currently blocked | No implementation begins until executed evidence exists | `CCD-022`, `docs/audits/apt_serve_official_artifact_audit_20260805.md` |
| Llumnix requires comparative evaluation before any classification | Passing fidelity tests ("execution-health clean") is not the same evidence class as a scored comparison against other policies — this project already applies that bar to every other faithful baseline and had, until this reconciliation, failed to apply it consistently to its own status documentation for Llumnix | 36/36 (188/188) tests passing; zero comparative-evaluation results found anywhere in the repository | Classification `UNESTABLISHED pending evaluation`, not `NOT_INTEGRATED` and not `VALIDATED` | `CCD-020`, `CCD-021`, `docs/audits/llumnix_official_artifact_audit_20260806.md` |
| Stress tests must include both target and counter regimes | A baseline's claimed mechanism (target regime) proves the mechanism can work; a stress test only becomes evidence against overclaiming once matching counter/adversarial regimes are also tested | Sarathi's 7-entry catalog (2 target + 3 counter + 2 literature-motivated) as the established pattern | Llumnix's 14-regime target/counter matrix (§12 of its audit) is scoped the same way, even though not yet built | `docs/research/algorithm_stress_tests/STRESS_TEST_CATALOG.md`, `docs/audits/llumnix_official_artifact_audit_20260806.md` §12 |
| Official code is preferred whenever public and importable/usable | Adapter-wrapping real, unmodified official code (VTC) is stronger evidence than any reimplementation, faithful or not | VTC's `VTCReqQueue` is a standalone, dynamically-importable class this project runs unmodified; contrast with Sarathi/Llumnix/Apt-Serve, all monolithic vLLM forks with no separable component (Strategy B ruled out structurally for all three) | Integration-strategy decisions (Strategy A/B/C/D) are evaluated per-baseline based on the artifact's actual structure, not a blanket policy | `docs/audits/llumnix_official_artifact_audit_20260806.md` §10, `docs/audits/apt_serve_official_artifact_audit_20260805.md` |
| Real-system and simulator tracks must be labeled separately | Conflating "faithful simulator reimplementation" with "the official system" would misrepresent evidence strength in any manuscript claim | Sarathi has both tracks (simulator + real Wulver A100 validation) and the project explicitly requires disclosure language distinguishing them; Llumnix currently has only the simulator track | Any claim about a faithful baseline must state which track (or both) it draws on | `docs/audits/llumnix_official_artifact_audit_20260806.md` §10, `docs/baselines.md` |
| Local and Wulver state must not be conflated | A same-day parallel research pass had already caught a task briefing wrongly asserting a Wulver job was "currently running" when local evidence showed it was blocked; the opposite error (assuming remote inactivity from local silence) is equally possible | `docs/audits/project_pause_reconciliation_query1_20260806.md`, `docs/audits/project_pause_reconciliation_query2_20260806.md` (Wulver auth diagnosis performed, not skipped) | Any Wulver-adjacent status must be labeled `REMOTE_STATE_UNVERIFIED` when direct access fails, never asserted as a confirmed negative | `CCD-023` |
