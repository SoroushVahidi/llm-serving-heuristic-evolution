# Selector Dataset v2 validity reassessment after `vllm_chunked_prefill_faithful`

Per task instruction, this classifies six selector-relevant workload
regimes after implementing and benchmark-pack-validating
`vllm_chunked_prefill_faithful` (see
`docs/vllm_chunked_prefill_faithful_scheduler_reference.md` and
`docs/vllm_chunked_prefill_faithful_root_cause_analysis.md`). **No Selector
Dataset v2 data is generated by this document or this task** -- this is an
assessment only.

Classification legend: `VALID_FOR_SELECTOR_DATASET` /
`VALID_ONLY_WITH_CALIBRATION` / `INVALID_UNTIL_SIMULATOR_EXTENSION` /
`REFERENCE_ONLY`.

## Summary table

| Regime | Classification | Why |
|---|---|---|
| `short_context` | `VALID_FOR_SELECTOR_DATASET` | Decode-dominated; the mismatches found (Findings 1-3, root-cause doc) are specific to scenarios with substantial competing prefill work, which short prompts structurally don't create. Unaffected by this session's findings. |
| `medium_context` | `VALID_FOR_SELECTOR_DATASET` | Same reasoning as `short_context` -- prefill cost is real but small relative to decode; not the regime where Finding 1/2 bite. |
| `long_context` | `VALID_ONLY_WITH_CALIBRATION` | **Structurally unblocked** by this baseline (see below) -- was `INVALID_UNTIL_SIMULATOR_EXTENSION` before this session (100% drop under `vllm_faithful`), now completes via genuine chunked admission, matching real vLLM's qualitative behavior. Not yet `VALID_FOR_SELECTOR_DATASET` because the *ranking* (which policy wins E2E) for long-context scenarios inherits the same Finding-1/2 timing-model caveats as every other regime below. |
| `prefill_heavy` | `INVALID_UNTIL_SIMULATOR_EXTENSION` | Real hardware shows robust, opposite-direction winners depending on the *specific* prefill/decode interaction shape (`prefill_heavy_burst`: vLLM wins; `active_decode_plus_arriving_prefill`: Sarathi wins) -- but the simulator currently ties on **both** under a fair timing model (root-cause doc's Addendum). A selector trained on this regime today would learn from ties/near-ties that don't reflect either real direction, not from calibration-fixable noise. |
| `decode_heavy` | `INVALID_UNTIL_SIMULATOR_EXTENSION` | Same underlying mechanism as `prefill_heavy` (Finding 2: `GPUState._step_phase15`'s `decode_first` branch is dead code, so decode protection is unconditional for every Phase-1.5 policy regardless of scheduling algorithm) -- `active_decode_plus_arriving_prefill` is the canonical decode-heavy-plus-arrival scenario and ties today. |
| `high_kv_pressure` | `VALID_ONLY_WITH_CALIBRATION` | The *structural* claim (`kv_progression` fixture: admission control prefers queueing new arrivals over evicting running work, zero preemption events even at 83.67% peak KV utilization) **is** correctly represented -- verified both by code inspection (`_schedule_prefills`'s only failure actions are "stop admitting"/"re-queue," never `bm.free`/preempt on a running request) and empirically (20 requests, 2000 tokens each, KV capacity for only ~3 concurrently: 0 preemptions, all 20 eventually complete via queueing). The *E2E timing/ranking* claim (`kv_pressure` scenario: Sarathi should win) is not (same tie as `prefill_heavy`/`decode_heavy`, Finding 1/2). |

## `long_context`: structurally unblocked -- the direct, task-mandated acceptance result

Before this session: `vllm_faithful` (pinned pre-chunked-prefill, v0.1.0)
admits a request's entire prompt in one shot or not at all; a ~12,000-token
prompt against a 2,560-token `max_num_batched_tokens` budget is **never**
admitted (`completion_fraction=0.0`, all 16 requests of the
`xlong_context_burst16` fixture sit in `waiting` forever). This was the
single largest structural gap in the external-baseline suite relative to
real vLLM (which, with chunked prefill enabled, completes all 16).

After this session: `vllm_chunked_prefill_faithful` completes the same
fixture with `completion_fraction=1.0` (verified directly --
`tests/test_vllm_chunked_prefill_faithful_benchmark_pack.py::
test_long_context_new_baseline_completes_all_16_via_chunked_admission`),
via genuine multi-step chunked admission (monotonic prefill progress,
verified in `tests/test_vllm_chunked_prefill_faithful_scheduler.py::
test_new_baseline_shows_monotonic_prefill_progress_across_chunks` and the
stress suite's `test_monotonic_prefill_progress_across_randomized_chunk_
sizes`), not by relaxing any capacity constraint.

**This closes the structural gap** (a long-context request trace can now
be run against a faithful vLLM-family baseline and produce a non-degenerate
result at all), which is a necessary precondition for `long_context` to
ever be `VALID_FOR_SELECTOR_DATASET`. It is not sufficient on its own: the
*winner identity* for a long-context scenario against `sarathi_faithful`
still depends on the same fair-timing-model requirement as every other
regime (evaluate under `ServiceModel(enable_prefill_modeling=True, ...)`
for both, not `vllm_faithful`'s historical zero-prefill-cost default -- see
root-cause doc Finding 1), and, per Finding 2/3, the specific "decode
stalled by competing prefill" dynamic that differentiates real vLLM from
real Sarathi in long-context-adjacent regimes is still not observable in
this simulator's execution layer for any policy. Hence
`VALID_ONLY_WITH_CALIBRATION`, not `VALID_FOR_SELECTOR_DATASET`: the
*existence* of a completed run is trustworthy; the *ranking* is not yet.

## Is the runtime-informed mismatch improved?

Partially, and in a specific, disclosed way:

- **Improved**: the long-context structural gap (the clearest, largest
  mismatch between simulator capability and real vLLM behavior) is closed.
  The two positive-target mismatches (`active_decode_plus_arriving_
  prefill`, `kv_pressure`) are now **root-caused** to two specific, named
  mechanisms (Finding 1: asymmetric `ServiceModel` config in the
  benchmark-pack-generating harness; Finding 2: dead `decode_first` code in
  `GPUState._step_phase15`) rather than left as "the simulator doesn't
  model this with enough fidelity" (the pre-existing, less actionable
  description).
- **Not improved**: the actual E2E-winner mismatch direction is not fixed
  by this baseline alone -- all five canonical request-level scenarios tie
  under a fair comparison (root-cause doc Addendum), including the three
  negative controls, which "passed" in the pre-existing numbers only
  because of the same Finding-1 asymmetry that caused the positive targets
  to fail. Closing this requires either revisiting `GPUState._step_phase15`
  (a shared-infrastructure change out of scope here -- would affect
  `sarathi_faithful`'s existing, relied-upon numbers) or accepting that
  this simulator abstraction cannot currently discriminate this specific
  class of scheduling difference at all.

## Is calibration still required?

Yes, for every regime marked `VALID_ONLY_WITH_CALIBRATION` above, and this
is a stronger, more specific statement than a generic disclaimer: the
*direction* of miscalibration is now known (all three `vllm_faithful`/
`sarathi_faithful`/`vllm_chunked_prefill_faithful` numbers tie at small
request scale under a fair config; the pre-existing asymmetric-config
numbers systematically favor whichever vLLM-family baseline gets the
zero-prefill-cost `ServiceModel()` treatment) -- future selector-label
generation should not treat any of these three baselines' *relative*
E2E-winner ordering as ground truth in a `prefill_heavy`/`decode_heavy`/
`high_kv_pressure` scenario without independently confirming which
`ServiceModel` each candidate policy is being scored under.

## Is repeated-trial ground truth sufficiently represented?

Yes, structurally: `experiments/runtime_validation_benchmark_pack/
hardware_targets/*.json` carries the full N=5 repeated-trial statistics
(mean/median/stdev/p50/p95 per metric per system) and the
positive-target/negative-control labeling is explicitly grounded in that
N=5 data, not the earlier single-run observations (see
`docs/runtime_validation_benchmark_pack.md`'s "Safe claims" section). This
was already true before this session and is unchanged by it -- the
limitation this session identifies is in the *simulator's* ability to
reproduce that ground truth, not in the ground truth's own statistical
representation.

## `READY_TO_RESUME_SELECTOR_DATASET_V2`: no, not for the full regime set

`short_context`/`medium_context` generation could reasonably resume on
their own (no mechanism identified this session affects them). But
per-regime partial resumption is not what "Selector Dataset v2 generation"
means in this project's existing pipeline (a single generation pass across
the full scenario taxonomy -- see `docs/research_status.md`), and
`prefill_heavy`/`decode_heavy`/`high_kv_pressure`/`long_context` are 4 of
the more selector-relevant, discriminative regimes specifically because
real hardware shows a large, robust winner-identity split across them
(exactly why they were chosen for the benchmark pack). Generating labels
for those regimes today would encode ties (from Finding 1/2) as if they
were genuine simulator judgments. Recommendation: do not resume full-scale
generation; a smaller, targeted pilot restricted to
`short_context`/`medium_context` plus the newly-unblocked `long_context`
completion-only structural cases (not winner-direction labels) is the
appropriate next step -- see this task's final report's
`NEXT_RECOMMENDED_ACTION`.

## Reassessment after the `decode_first` fix

Per `docs/decode_prefill_contention_execution_model.md`: `GPUState.
_step_phase15`'s dead `decode_first` branch (this document's Finding-2
citation for why `prefill_heavy`/`decode_heavy` were `INVALID_UNTIL_
SIMULATOR_EXTENSION`) has been fixed, opt-in and backward-compatible. The
"simulator extension" these two regimes were waiting on has landed: decode
and prefill requests can now genuinely contend for a shared per-step
budget (`ServiceModel(enable_decode_prefill_contention=True, decode_first=
False)`), and a decode-phase request CAN now receive zero progress in a
step because an earlier-arrival prefill request exhausted the budget --
verified directly (`tests/test_decode_prefill_contention_execution.py`) on
a constructed scenario.

Revised classification:

| Regime | Old classification | New classification | Why it changed |
|---|---|---|---|
| `short_context` | `VALID_FOR_SELECTOR_DATASET` | `VALID_FOR_SELECTOR_DATASET` (unchanged) | Decode-dominated; not the regime this fix touches. |
| `medium_context` | `VALID_FOR_SELECTOR_DATASET` | `VALID_FOR_SELECTOR_DATASET` (unchanged) | Same. |
| `long_context` | `VALID_ONLY_WITH_CALIBRATION` | `VALID_ONLY_WITH_CALIBRATION` (unchanged) | Structural completion was already fixed by `vllm_chunked_prefill_faithful` itself, independent of `decode_first`; the ranking caveat is unchanged by this fix (verified: `xlong_context_burst16` completion_fraction stays 1.0 under the new contention mode -- see the runtime-benchmark-pack revalidation). |
| `prefill_heavy` | `INVALID_UNTIL_SIMULATOR_EXTENSION` | **`VALID_ONLY_WITH_CALIBRATION`** | The blocking condition ("decode protection is unconditional for every policy regardless of scheduling algorithm") is resolved -- the mechanism is now genuinely representable. Not yet `VALID_FOR_SELECTOR_DATASET`: the runtime-benchmark-pack revalidation shows the current canonical `prefill_heavy_burst`/`mixed_prompt_lengths` fixtures don't happen to exercise the new divergence (see that doc's arrival-order audit) -- ranking validity against real hardware for this regime is unverified, not disproven. |
| `decode_heavy` | `INVALID_UNTIL_SIMULATOR_EXTENSION` | **`VALID_ONLY_WITH_CALIBRATION`** | Same reasoning as `prefill_heavy` -- `active_decode_plus_arriving_prefill` is the canonical decode-heavy-plus-arrival scenario; the mechanism is now representable but that specific fixture's decode-eligible requests all arrive no later than the competing prefill requests, so it still ties post-fix (verified). |
| `high_kv_pressure` | `VALID_ONLY_WITH_CALIBRATION` | `VALID_ONLY_WITH_CALIBRATION` (unchanged) | `kv_pressure`'s own fixture has all 12 requests arriving simultaneously (t=0) -- the FCFS-by-arrival tie-break is identical under both execution models for simultaneous arrivals, so this fix doesn't change its (already-ties) outcome. Preemption-avoidance structural claim, already correctly represented, is unaffected either way. |

### `READY_TO_RESUME_SELECTOR_DATASET_V2`: still no

This fix removes a structural blocker for two regimes but does not, by
itself, produce a single validated winner-direction label anywhere it
didn't exist before -- every canonical benchmark-pack fixture re-run under
the corrected mechanism still ties (see `docs/decode_prefill_contention_
execution_model.md`'s Revalidation section). Resuming full-scale Selector
Dataset v2 generation today would still risk encoding these ties as if
they were genuine simulator judgments for `prefill_heavy`/`decode_heavy`.
The appropriate next step is unchanged in kind, widened in scope: a
targeted pilot using `short_context`/`medium_context`/`long_context`
(structural, as before) COULD now also probe `prefill_heavy`/`decode_heavy`
specifically with fixtures engineered so a decode-phase request arrives
after a competing still-prefilling request on the same GPU (the one
interaction shape none of the six existing canonical fixtures happens to
construct) -- not as label generation, but as a targeted validation of
whether the newly-representable mechanism, once actually exercised,
reproduces the real-hardware Sarathi-advantage direction. See this task's
final report's `NEXT_RECOMMENDED_ACTION`.
